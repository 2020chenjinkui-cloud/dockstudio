## 4. 线 3：1HSG 真实 redocking RMSD（t3 / `qa/redock-1hsg` @ `3946037`）

4 个新增文件、+1294 行（报告 497 行 + 3 个复现脚本），`server/dockstudio/**` 零改动。
条件：共晶配体真实立体异构体、vina 1.2.7、`exhaustiveness=8`、`seed=42`、盒子 = MK1:B 质心 22.5 Å 立方、cpu 4。

| 口径（函数） | 数值 | D9 判据（≤2.0 Å） |
|---|---|---|
| top1 pose RMSD — `analysis/crystal.py::heavy_atom_rmsd`（`rdMolAlign.GetBestRMS`，对称校正 **+ 叠合**） | **0.380 Å** | PASS |
| best-of-N RMSD（N=9，同口径取最小） | **0.380 Å** | PASS |
| symmetry-corrected **原位**（`rdMolAlign.CalcRMS`，不叠合） | **0.454 Å** | PASS |
| `exhaustiveness=32` 复测（三口径） | 0.553 / 0.428 / 0.598 Å | PASS |

出处：`docs/qa/redocking-1hsg-2026-11-18.md` §0 / §5.1；同机重复 A/A2 的 top1/best/原位与亲和力逐位一致。

**三处结构性缺陷（会让不达标的对接显示绿色；报告 §7.2）**
1. **度量函数选错**：`heavy_atom_rmsd` 底层 `GetBestRMS` 先叠合再算 RMSD。把正确姿态整体平移 +10 Å，平台值仍报
   **0.380 Å**，而 `CalcRMS` 从 0.454 → **9.903 Å**；27 个姿态中 **6 个**"平台 ≤2 Å 但原位 >10 Å"。
2. **redock 的分子不是共晶配体**：`demo_data/indinavir_smiles.txt`（示例/测试/历史 E2E 都用它）是无立体 SMILES，
   落地 3D 是 MK1 的**非对映体**（`CBVCZFGXHXORBI-RXFGFDIZSA-N` vs 晶体 `…-PXQQMZJSSA-N`），仍报 1.075 Å"通过"；
   只换 ETKDG 准备种子 → 4 个种子给出 **4 个互不相同的 InChIKey**，平台口径 1.075 / 2.338 / 0.899 / 0.898 Å，
   原位 1.104 / 4.152 / 0.940 / 0.988 Å。
3. **不可复现**：`DockParams.seed` 默认 `None`（`models.py:31`）；两次历史记录缺 seed / vina 版本 / exhaustiveness / 度量口径。

**历史 4.226 Å（Windows）/ 2.104 Å（macOS）的差异来源（报告 §6）**：同机同版本下改 Vina 种子只能动到 1.08–1.22 Å
（6 次运行 / 4 种种子设置），`exhaustiveness` 2/8/32 也只到 1.185 / 1.075 / 0.553 Å；真正能把 RMSD 推到 2.3–4.2 Å 的
是**配体身份 / 准备环境**（无立体 SMILES → ETKDG 随机指派决定是哪个非对映体）。即历史超标主因是配体身份不确定，
不是引擎或参数。

另：由平台自己抽出的共晶 SDF（无键级）反建配体会静默变成饱和类似物（`C36H69N5O4` vs `C36H47N5O4`），
直接 FAIL（**3.641 Å**）且无告警（报告 §3.4）。

### 13.2 T12-F1（Windows 可执行性）闭环 —— 并**更正**此前关于 windows-latest 的表述

**此前表述（错误，见 §12.6-C / t11 报告 §6）**：「把 `#!/bin/sh` stub 换成 `#!<python>` 的 Python stub
后，windows-latest 不再新增失败」。

**更正**：这句话**不成立**。Python 脚本的 shebang 只在 POSIX 由内核解释；Windows 的 `CreateProcess`
不经 shell、不读 shebang，`.py` stub 在那里根本无法作为可执行程序启动 —— 那 5 个用例在
`windows-latest` 上会**失败**，而不是通过。

**判定依据（t14 实测，不是推断）**：在 Linux 上删掉 shebang → 内核返回 `ENOEXEC`
（`[Errno 8] Exec format error`），与 Windows 的失败模式一致；用 pytest 插件在测试期做该替换 →
`test_gnina_rescore_fix.py` **5 failed / 11 passed**，失败集合与 t12 点名的完全一致。

**修法**：6 个依赖"可执行 stub"的用例（`test_gnina_rescore_fix.py` 5 个 + `test_gpu_adapters.py::test_gnina_mock_binary_e2e`）
加 `@pytest.mark.skipif(sys.platform == "win32", reason=…)`；不提供 Windows launcher（`.bat` 等于再绑一次平台 shell，
给适配器加 `sys.executable` 后门只为测试存在会污染生产路径）。

| 验证 | 结果 |
|---|---|
| 模拟 `sys.platform == "win32"`（两文件） | **19 passed / 8 skipped**（6 条本 finding + 2 条既有 off-linux） |
| Linux（同两文件） | **25 passed / 2 skipped**（无回退） |
| T15-F4 顺带收窄 | `except Exception: pytest.skip` → `except OSError`；`-rs` 确认只剩 2 条既有 off-linux skip，无意外 skip |

### 13.3 T12-F2（协作取消记账）闭环 —— 修的是判据层级，不是措辞

**修前实测（t14，n=12）**：tier3 中途取消 → `candidates=1` / `n_funnel_filtered=11` / **`is_conserved=True`** / 无 `aborted` 行；
tier2 中途取消（keep1=0.5）→ `filtered=12` / `conserved=True` / 无 `aborted` 行。
即「被中止」被当成「阈值淘汰」吸收掉，报告看起来完整。

**根因**：`_abandoned_ligand_ids()` 问的是"有没有任何 checkpoint 记录"，而 tier2/tier3 取消时这些分子
早在 tier1 就 checkpoint 过 → 被判为"处理过"。

**修法**：按 tier 记账（`_tier_truncated: dict[int, set[str]]` + `_record_tier_truncation()`），三个 tier 循环结束后各记一次；
`run()` 两个早返回分支把上一层幸存者记为下一层的截断（否则取消落在 tier 边界会少报 1 个，实测 `aborted=5` 而实际 6 个未评估）。
**明确不用残差兜底**（`residual = pool − success − failed − filtered`）：它会把 tier3 的 QC 淘汰
（`HIGH_STRAIN_UNCONVERGED_FALLBACK` 等本就不计入 filtered）误标成"被中止"，让正常跑完的筛选看起来"被取消"。

| 场景（n=12） | 修前 | 修后 |
|---|---|---|
| tier3 中途取消 | candidates=1 / filtered=11 / **conserved=True** / 无 aborted | candidates=1 / **filtered=0** / **conserved=False** / **aborted=11** |
| tier2 中途取消（keep1=0.5） | candidates=0 / filtered=12 / **conserved=True** / 无 aborted | candidates=0 / **filtered=6**（真实 12→6 比例淘汰）/ **conserved=False** / **aborted=6** |
| 完整跑完（反向对照） | — | filtered=0 / **conserved=True** / 无 aborted 行（未误伤） |
