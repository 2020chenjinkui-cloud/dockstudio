### 3.3 版本漂移：lint 门在新 ruff 下从 29 条涨到 226 条（实测）

所以规则集完全由 ruff 的默认值决定。而 `server/pyproject.toml` 的 dev extra 是
`ruff>=0.4,<0.17` —— CI 装出来就是 0.16.x。逐个版本实测（临时 venv 装的 4 个版本，
`/tmp/ruffhist/`）：

| 0.15.0 | **29 errors** | 19 files |
| **0.16.0** | **226 errors** ← 默认规则集在这里变宽 | 19 files |

- 0.15.0 的 29 条构成：`F401×14, E402×7, E741×3, E731×1, F541×1, F811×1, F821×1, F841×1`
  （= 历史默认集 `E4,E7,E9,F`，`--select E4,E7,E9,F` 在 0.16.10 下复现同样 29 条）
- 0.16.0 起默认启用面扩大：`ruff check server/dockstudio --show-settings` 显示
  **412 条规则被启用**（含 BLE/S/SIM/PERF/PLR/C414/RUF/PYI/UP/PIE…），

这是本轮第 4 条线（lint/format 门禁修复）的输入。

即：**168 处兜底异常里，136 处（168−32）没有被任何 noqa 标记**，
其中 129 处被 BLE001 直接点名、7 处虽只做转译但同样吞掉了原始异常类型。

- **l1** = l0 + `pytest tests -q -m "not golden"` 再 `--ignore` 掉 10 个重活文件

- 每步一份日志到 `/tmp/dockstudio-gates/<时间戳>-<步骤>.log`，失败会打印日志路径和 rc
- 退出码：`0` 全绿 / `1` 有步骤失败 / `2` 参数或环境错误

## 5. 本轮已知问题清单

> 编号只为引用方便，不代表优先级排序。

**K1. lint 门在干净环境必红（CI 会红）**
`.github/workflows/ci.yml` 的 `server-test`（push/PR 必跑）里 Lint 步骤就是
`ruff check server/dockstudio`，没有任何 `select`/版本锁定，dev extra 是
`ruff>=0.4,<0.17`。当前 ruff 0.16.10 下 **226 errors**，退出码 1。实测 0.16.0 起
默认规则集变宽（29 → 226，见 3.3），所以"以前是绿的"这个印象对 0.16 不成立。

**K2. 226 error 的规则分布**：25 条规则，前 5 条 `BLE001 133 / S110 37 / F401 14 /
I001 6 / S112 5` 占 86.3%（完整表见 3.1）。其中 32 条可用 `--fix` 自动修。

**K3. 19 个文件待格式化**，与 ruff 版本无关（0.4.10 ~ 0.16.10 都是 19 个），
清单见 3.2；`ruff format` 一跑就是 19 文件的 diff，需要单独一个 commit 处理。

**K4. `F821` — `cli/commands/engines.py:48` 的 `Any` 未导入**
`def build_engines_pane() -> Any:`，文件内无 `from typing import Any`。因
`from __future__ import annotations` 运行期不炸，但类型检查/反射全失效。

**K5. `F811` — `prep/receptor.py:319` 的 `_Chem` 重复导入**
模块级第 18 行已 `from rdkit import Chem as _Chem`（带 `# noqa: F401`），
函数内第 319 行又局部重导一次；连带的 RUF100 有 3 处（export.py:9、interactions.py:14、
receptor.py:20 的 `I001` 无用 noqa）。

**K6. 168 处 `except Exception`，只有 32 处带 `# noqa`**（核账见 3.5）。
"静默科学降级"的代码根源规模已经量化：136 处未标注。

**K7. 全量测试在 CI 条件下也不是绿的**
Run B（引擎可用 = CI 条件）`1 failed, 497 passed, 13 skipped`，失败项是
`test_adversarial_m3_challenger2.py::test_mid_run_crash_simulation_at_7_and_19_zero_loss_resume`
（`DID NOT RAISE KeyboardInterrupt`），且该用例结果在不同上下文里不稳定
（单独跑 5/5 失败、全量 Run A 却通过）。**任何"本轮全量通过"的结论都必须先处理它，
否则等于用一个不可靠用例的偶然通过当证据。**

**K8. 干净 worktree 没有引擎，会造出假红**
`resources/bin/` 被 `.gitignore` 忽略，新 worktree 完全没有引擎二进制，
`tests/test_cli_agent.py::test_dock_demo_and_post_dock_actions_end_to_end` 会因
`EngineUnavailableError` 失败。测基线/跑门禁必须显式接引擎
（`run_gates.sh` 已自动注入）。

**K9. `gnina --version` 是硬编码字符串**
`resources/bin/linux-x86_64/gnina` 是 bash wrapper，对 `--version` 直接
`echo "gnina 1.3.3"`。任何依赖"探测版本"的逻辑在 Linux 上拿到的都是这行字；
真实二进制在 `/home/kui/engines/gnina`，自报 `gnina v1.3.3 master:6fe1ce2 Built Jun 30 2026.`。

**K10. 本机/CI 的 Python 小版本不一致**：本机 3.11.15，CI `server-test` 是 3.12。
基线数字只对 3.11.15 成立。
